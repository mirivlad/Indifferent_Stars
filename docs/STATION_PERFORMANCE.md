# Рывки и задержка ввода рядом со станцией

Проверка 2026-11-03. Первый раздел сравнивает исходную и исправленную реализацию
на станции 55 м/ед. с 11 692 треугольниками. Ниже отдельно приведён повторный прогон
на увеличенной станции 275 м/ед., с 15 676 треугольниками и настоящей подсветкой.
Архив исходных JSON и SHA-256: [данные](performance/station-approach-2026-11-03/sha256.json).

## Причины и изменения

Точные непрерывные коллизии начинали дорогой обход пар треугольников ещё внутри
пустой области общего bounding sphere. Добавлены консервативная проверка достижимости
оболочки всем корпусом с учётом относительного перемещения/вращения, AABB отдельных
треугольников и повторное использование преобразованных узлов/треугольников BVH
в пределах одного временного среза. Рабочие массивы берутся из ArrayPool и возвращаются
через finally. Форма оболочки, шаг симуляции, SAT и допуск вращения 5 см сохранены.

Отдельно обнаружена постоянная задержка клиентской шкалы времени. Обработка очереди
после загрузки привязывала первый старый снимок к текущему времени; следующие снимки
сохраняли ошибку этой привязки. В реальном клиенте отображаемое состояние оказалось
примерно на 325 мс позади свежих пакетов даже при ровных кадрах и сети.

Пакеты теперь получают отметку времени в потоке приёма, до обработки главным потоком.
ShipTrack сохраняет интервалы серверного времени, но не разрешает накопленной очереди
уводить снимки в будущее. При паузе шкалы более 250 мс восстанавливается интерполяция;
начальная локальная точка spawn не смешивается с авторитетной временной шкалой.
Обычный буфер собственного корабля остаётся 50 мс, удалённых — 110 мс.
Камера, управление, модель, материалы и качество рендера для этой оптимизации не упрощались.

Локальный запуск `tools/run-local.sh` собирает и запускает сервер в Release.
Debug остаётся доступен для отладки, но не используется как обычная игровая сборка сервера.

## Условия и CPU

Debian/Linux, Xeon E5-2680 v4 2,40 ГГц, 28 логических CPU, .NET 10; seed 20261101,
8 NPC, один тестовый пилот, шаг симуляции 50 мс. Diagnostics измеряет Stopwatch-время
непосредственно вокруг запроса или GameWorld.Tick, после 8 прогревов, 64 образца на сценарий.
Для сопоставимости двух сборок явно задан `DOTNET_TieredCompilation=0`.

| Полный тик, Release, p95 | До | После |
| --- | ---: | ---: |
| Пустой проход кольца | 2,076 мс | 0,428 мс |
| Зависание над ободом | 5,003 мс | 1,450 мс |
| Контакт с ободом | 0,448 мс | 0,462 мс |
| Возле центрального узла | 0,587 мс | 0,616 мс |

Контакт и центральный узел существенно не ускорились; небольшой абсолютный разброс
нельзя выдавать за статистически значимую регрессию или улучшение. Главный выигрыш —
свободное пространство, где полный SAT не нужен либо многократно повторял вычисления.
Сам Sweep после прогрева не выделяет память; полный тик в этом сценарии сохранил
2120 байт выделений на вызов. В Debug зависание над ободом снизилось с 46,30 до 15,31 мс
на полный тик; при обычной игре используется проверенная Release-сборка.

```bash
DOTNET_TieredCompilation=0 dotnet run -c Release \
  --project tools/IndifferentStars.Diagnostics -- /tmp/station-cpu.json
```

Это замер CPU-работы конкретной симуляции, не GPU-время и не обещание FPS/числа игроков.

## Настоящий клиент, ввод и кадры

Godot 4.7.2 .NET, Forward+, Radeon RX 580 2048SP / RADV POLARIS10,
1600×900, render scale 1, MSAA 4×, bloom и солнечные тени включены, VSync.
Один графический клиент и второй независимый UDP-клиент, 8 NPC, 380 астероидов,
локальный авторитетный сервер Release, снимки/тики 20 Гц. На подходе используются
обычные публичные приказы полёта, затем синтетические клавиши Godot, по 6 нажатий на вид.
Измерение заканчивается при видимом изменении ориентации камеры примерно на 0,5°;
задержка физической клавиатуры, оконного композитора и дисплея сюда не входит.

| p95 | До исправления шкалы | После |
| --- | ---: | ---: |
| Нажатие → камера F2 | 417,3 мс | 116,1 мс |
| Нажатие → камера F3 | 381,4 мс | 151,1 мс |
| Возраст отображаемого серверного состояния F2 | 324,9 мс | 30,0 мс |
| Межкадровое время F2 | 17,403 мс | 17,376 мс |
| Межкадровое время F3 | 17,359 мс | 17,368 мс |

Снимки приходили примерно каждые 51 мс в обеих версиях. Это показывает, почему
одной проверки FPS или ping недостаточно: источник задержки находился в интерполяции.
Первый прогон провалил установленную проверку отклика p95 < 250 мс; после исправления
прошли оба вида. Это небольшой воспроизводимый локальный сценарий, не общий сетевой SLA.

```bash
dotnet run -c Release --project src/IndifferentStars.Server -- --port 17896
# В другом терминале, с отдельным профилем тестового клиента:
XDG_DATA_HOME=$(mktemp -d) IS_APPROACH_CAPTURE=/tmp/station-approach \
  "$GODOT_BIN" --path client res://tests/StationApproachChecks.tscn \
  --resolution 1600x900 --audio-driver Dummy -- --server 127.0.0.1:17896
```

## Регрессии

Регрессия очереди снимков воспроизведена до исправления и пройдена после него;
проверяется и восстановление после паузы сервера. Контактные тесты дополнены неподвижным
малым корпусом, в который входит вращающееся препятствие, и быстрым относительным
движением двух корпусов. Это защищает ранний отсев от пропуска настоящего столкновения.

## Станция после увеличения в пять раз

Те же CPU/GPU, разрешение 1600×900, Forward+, render scale 1, MSAA 4×, VSync,
свечение, солнечные тени и тени четырёх прожекторов. Сервер Release, два независимых
клиента, 8 NPC в симуляции, 380 астероидов. Станция: 275 м/ед., 15 676 треугольников,
24 местные лампы и 4 прожектора. Fingerprint `a5fca29a1bca3a5cc7d11f6ac046e980b7873ede1b98166d91855cbc1184a21f`.

| p95 | Увеличенная станция |
| --- | ---: |
| Межкадровое время на подлёте, 1063 кадра | 17,477 мс |
| Межкадровое время F2, 359 кадров | 17,390 мс |
| Межкадровое время F3, 339 кадров | 17,363 мс |
| Нажатие → камера F2, 6 нажатий | 133,4 мс |
| Нажатие → камера F3, 6 нажатий | 100,5 мс |
| Возраст отображаемого состояния F2 / F3 | 31,7 / 31,5 мс |
| Интервал снимков F2 / F3 | 51,3 / 50,9 мс |

Оба пилота подошли обычными двигателями; точки зависания подняты над оборудованием
крыши с запасом на торможение. Прежние низкие точки приводили к настоящему касанию
оболочки при торможении, после которого корабль получал касательную скорость станции,
а приказ прекращался. Это не было зависанием ввода. Точность коллизий сохранена;
отдельная CPU-проверка `rim_close` измеряет работу всего в 7 м над кромкой.

Максимум одного кадра подлёта — 110,44 мс, F2 — 33,97 мс, F3 — 17,76 мс.
Таким образом, регулярная задержка очереди устранена в этом сценарии, но этот прогон
не доказывает отсутствие единичных кадров загрузки/прогрева. p95 не скрывает эту оговорку.
После увеличения также пройдены реальная стыковка/рынок/отстыковка во всех видах,
выход на безопасную дистанцию, варп к точке карты, планете и через AU с переносом origin.


В отдельном прогретом CPU-прогоне Release при `DOTNET_TieredCompilation=0` полный тик
с 8 NPC показал p95: свободное кольцо 0,384 мс, зависание над ободом 0,374 мс,
`rim_close` в 7 м над кромкой 2,076 мс, контакт 2,111 мс, центральный узел 1,026 мс,
причал 0,418 мс. 64 образца на сценарий, шаг 50 мс. Sweep после прогрева без выделений,
полный тик — 2120 байт. Эти числа относятся к новым размерам и точкам, поэтому их нельзя
напрямую вычитать из прежней таблицы станции 55 м/ед.
