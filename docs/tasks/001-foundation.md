# Task 001 — First Flight: первый играбельный прототип

**Приоритет:** P0  
**Статус:** ready  
**Ветка:** `feat/first-flight` от `main`  
**Результат:** пользователь на Debian **запускает игру, садится в корабль, летает по красивой системе, переключает 2D/3D/кокпит, видит NPC и может подключить второй клиент**.

## Зачем

Пользователь хочет **пощупать игру руками после первого захода агента**, а не получить только скелет репозитория. Первое впечатление от Indifferent Stars должно одновременно демонстрировать красивый космос и архитектуру с отдельным авторитетным сервером.

Прочти `AGENTS.md`, `docs/GAME_DESIGN.md`, `docs/ARCHITECTURE.md`. Реализуй именно этот законченный вертикальный срез. Не расползайся в галактику, экономику, PvP, регистрацию и производство.

## 1. Репозиторий и запуск

Создай отдельную ветку `feat/first-flight`. Ничего не коммить в main. Подготовь:

- Клиент на Godot 4.7.2 **.NET / C#**.
- Самостоятельный headless-сервер на .NET 10 / C# (без Godot).
- Общие сетевые DTO и отдельную чистую серверную симуляцию; простой `dotnet test`.
- Минимальный проверенный `.gitignore`.
- `README.md` с точными, проверенными командами Linux: 1) сервер, 2) клиент, 3) второй клиент, 4) тесты. Скрипт `tools/run-local.sh` — плюс, если надёжен.
- Запуск без обязательной PostgreSQL, Docker, облака, аккаунта, внешних ассетов и подключения к интернету. Для localhost должно хватить .NET SDK 10 и Godot .NET; работа должна быть возможна без sudo.

Если `godot-dotnet` не в PATH, документируй, как передать путь к редактору через переменную `GODOT_BIN`; не перезаписывай системный `godot`.

## 2. First Flight — что видит игрок

После запуска появляется **живая, красивая стартовая система** (временное имя допустимо):

- звезда с выразительным мягким свечением и ощущением глубины;
- крупная планета/газовый гигант с заметными кольцами **или** атмосферой;
- разреженный астероидный пояс из разноразмерных тел;
- простая, но различимая космическая станция с огнями и точкой интереса;
- несколько NPC-кораблей, двигающихся по повторяемым маршрутам **на сервере**;
- собственный корабль — узнаваемый силуэт, не просто дефолтный куб; достаточно процедурных примитивов с грамотными материалами;
- фон, цветовая композиция, контраст, дальние звёзды, масштаб, простые звуковые эффекты допустимы. Никакой зависимости от непроверенной коммерческой музыки.

**Важно:** сделать приятно выглядящий рабочий прототип, а не большой фотореалистичный проект. Допустима стилизованная геометрия, процедурные материалы, простой glow, мягкие акценты и один качественно оформленный вид. Цель — ощущение космоса, который хочется разглядывать. Предусмотри возможность отключения тяжёлых эффектов и не используй огромные текстуры.

## 2.1. Blender для стартовых моделей

Используй **Blender, если он установлен и доступен агенту**, для 1–2 выразительных базовых моделей: управляемого корабля и простого модуля станции (или другого элемента, который выиграет от ручного моделирования). Приветствуется генерация через `bpy` по скриптам в `tools/art/`, сохранение источников и экспорт `.glb` для Godot.

**Не требовать Blender MCP:** `blender --background --python script.py` — полноценный предпочтительный способ автоматической сборки ассетов без плагинов. Если Blender отсутствует или клиент OpenCode работает в изолированной среде, допустим процедурный резервный вариант прямо в Godot; укажи это в отчёте. Не устанавливай сторонние MCP-расширения автоматически.

Внешность модели проверяй не только по факту успешного экспорта, но и через рендер-превью либо скриншот в Godot. Не мешай основному рабочему прототипу из-за детализации моделей.

## 3. Можно реально летать

- Управляемый корабль с видимой ориентацией, инерцией/плавным разгоном и торможением, ограничением скорости, непрерывным движением по 3D-координатам. На M0 допустима аркадная модель, документируй.
- Управление клавиатурой должно быть понятным, с подсказками на экране. Предлагаемый базовый набор: `W/S` ускорение/торможение, `A/D` поворот, `Q/E` вертикальная тяга, `Shift` временное ускорение, `Space` тормоз; адаптируй разумно. Не полагайся только на мышь.
- `F1` — **полноценное 2D-навигационное представление**; `F2` — внешняя 3D-камера; `F3` — вид из кокпита. Вид меняется моментально, **не меняя координаты и скорость**.
- В 2D показывай собственный корабль, станцию, пояс, другие корабли, дистанции и знак/значение относительной высоты. Это должна быть **играбельная 2D-навигация**, а не просто окно с картой для варпа. В ней доступны движение и выбранное ниже действие.
- В 3D и кокпите должны быть те же возможности управлять движением и выполнять выбранное действие. В кокпите допустим минимальный процедурный интерьер / приборная рамка, но не просто переключение на камеру без HUD.
- Простой HUD: скорость, режим вида, цель (при наличии), расстояние до неё, доступные клавиши, состояние соединения.
- Желательно: локальный выбор станции/пояса в качестве точки интереса и кнопка перехода на короткую дистанцию (простой **тестовый варп**), доступная одинаково из всех видов. Это **stretch goal**, нельзя ради него бросить полноценное управление или сеть.

## 4. Минимальное настоящее взаимодействие

Реализуй одно законченное действие с серверной проверкой: **сканирование астероида или станции**.

- Игрок выбирает доступную цель с навигации/HUD (можно автоматически ближайшую в ограниченном радиусе или нажатием `Tab`).
- Нажатие `F` отправляет команду серверу.
- Сервер проверяет цель, дистанцию и принадлежность управляемого корабля. Возвращает результат: название/тип объекта, небольшой содержательный параметр (например, состав астероида).
- Результат отображается в UI **во всех трёх видах**.
- Действие не должно быть «локальной визуальной заглушкой».

Если добавляешь короткий тестовый варп, используй тот же принцип: команда, серверная валидация, одинаковое поведение в 2D/3D/кокпите. Не нужно полноценной механики топлива.

## 5. Сетевой фундамент

- Клиент отправляет **input/commands**, а не координаты.
- Сервер авторитетно обновляет положение игроков и NPC, выдаёт snapshots с версией протокола, номером шага/последовательностью.
- Два запущенных клиента видят **два разных корабля**, движение друг друга и одни и те же NPC. Выход клиента корректно удаляет его корабль у остальных.
- Локальный запуск 127.0.0.1 должен быть воспроизводимым. Адрес и порт сервера конфигурируемые.
- Интерполяция позиций других кораблей желательна; отсутствие интерполяции должно быть обозначено как ограничение.
- Никаких обязательных Docker/DB, внешних сервисов и облачной авторизации.
- M0 — проверка LAN/localhost, а не публичный интернет-сервис: не объявлять его защищённым от злоумышленников.

## 6. Чёткая граница работ

**Обязательно:** работающие сборки, сервер, полёт, 3 представления, симпатичная система, реальные NPC, сканирование, 2 клиента, инструкция запуска и базовые тесты.

**Не делать в Task 001:** тысячи систем, экономику, торговлю, полноценную добычу, инвентарь, вооружение, PvP, станции с интерьерами, обучение NPC, генерацию галактики, полноценный MMO-бэкенд, масштабирование на 300 игроков, сохранения, синхронизацию через интернет-сервис.

Если времени/контекста недостаточно, сначала доведи обязательный критический путь до запуска (сервер → клиент → полёт → три вида → второй клиент), затем NPC → сканирование → визуальная полировка. Не отдавай несобирающийся прототип ради дополнительного красивого шейдера.

## 7. Условия готовности (Definition of Done)

1. На Debian можно открыть Godot .NET проект и запустить клиент из редактора.
2. Сервер запускается в терминале через `dotnet run` или документированный скрипт, без окна и без Godot.
3. Видно достаточно оформленное космическое окружение: звезда, планета с кольцами/атмосферой, пояс астероидов, станция, NPC.
4. Игрок реально управляет кораблём и может в любой момент переключаться `F1/F2/F3`. После переключения корабль не телепортируется, не останавливается и не пересоздаётся.
5. В каждом представлении можно и летать, и выполнить одно и то же действие сканирования; в 2D показана относительная высота.
6. Два клиента одновременно подключаются, движутся независимо, видят друг друга и тех же NPC.
7. Сервер подтверждает действия; клиент не может сообщением с произвольной координатой переместить свой корабль.
8. Есть автоматические тесты фиксированного шага, валидации команды/принадлежности и сериализации/версии протокола.
9. `dotnet build`, `dotnet test`, доступные проверки импорта/сборки Godot прошли; если какой-либо инструмент недоступен, это прямо указано.
10. README содержит конкретные горячие клавиши, способ подключения второго клиента и раздел «Что пока не работает».

## 8. Отчёт

Создай PR из `feat/first-flight` в `main`. В отчёте:

- список реализованного;
- точные команды запуска (проверенные);
- результаты тестов и ограничений;
- при возможности 2–3 скриншота различных видов;
- что из желательного (тестовый варп, эффекты) оставлено на потом.

**Не сливай PR и не выпускай релиз без владельца.** Главный критерий — пользователь может сесть за компьютер и немедленно проверить **первый полёт**.
