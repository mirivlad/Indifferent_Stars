# Indifferent Stars — техническая архитектура (контракт для M0)

**Статус:** стартовые принципы, не окончательная схема. Читать вместе с [GAME_DESIGN.md](GAME_DESIGN.md) и [первым заданием](tasks/001-foundation.md).

## 1. Разделение системы

```text
 +----------------------------------------------+
 | Godot .NET client                             |
 | input / HUD / 2D / external 3D / cockpit      |
 +----------------------+-----------------------+
                        |
                versioned UDP protocol
                        |
 +----------------------v-----------------------+
 | .NET 10 dedicated server                      |
 | authoritative simulation / ships / world     |
 +----------------------+-----------------------+
                        |
                persistence (later)
```

- `client/`: проект Godot .NET на C#, сцены, управление, шейдеры, аудио, интерфейс.
- `server/`: headless-консольное .NET 10 приложение — отдельное от Godot.
- `shared/`: сетевые структуры и контракт сообщений, без `Godot.*`.
- `simulation/`: состояние игрового мира, шаг симуляции, правила команд, без графики.
- `tests/`: тесты симуляции, протокола и интеграции.
- `tools/`: проверенные команды/скрипты для Linux.

Допускается немного другая структура при сохранении принципов.

## 2. Воспроизводимый цикл

Сервер получает **команды**, валидирует их и по фиксированному таймеру обновляет состояние. Клиенты получают снимки и визуализируют их. Клиенты **не отправляют координаты как истину**. В качестве начальной гипотезы: 20 тиков/с и 10 снимков/с, параметры должны конфигурироваться.

Для M0 достаточно простой полётной модели с ограничением скорости, плавным разгоном/торможением и управлением поворотом. Реалистичность ньютоновской физики пока не фиксирована. Серверный tick и sequence передаются вместе со снимками. Клиент должен уметь интерполировать позиции других кораблей, не дёргая камеру.

## 3. Координаты

Иерархия адресации: `SystemId + SectorId + LocalPosition3D`. Для одной стартовой системы можно использовать один сектор, но никаких глобальных float32 координат на астрономических расстояниях.

Серверное положение хранить в достаточно точном формате (например, double); клиент преобразует в локальные координаты Godot относительно камеры. Сразу определить единую систему осей и единицы измерения в коде, README и тестах. Все три представления отображают **одну** 3D-позицию и сохраняют третью ось.

## 4. Протокол

- Предпочтительный транспорт: LiteNetLib / UDP, на основе документированных актуальных API пакета.
- Версия протокола; Hello/Join, JoinAccepted/Rejected, Input, Snapshot и Disconnect — достаточный состав для M0.
- Валидировать длину и содержимое сообщений, команды и принадлежность корабля.
- Для критичных событий использовать подтверждаемую доставку; частые снимки не должны блокировать симуляцию.
- Для M0 достаточно локальной сети/localhost: не выдавать незашифрованный тестовый сервер за безопасный публичный.
- Нет обязательной внешней авторизации, платных API, интернет-запросов или сетевой инфраструктуры для одиночной игры.

## 5. Одни правила для 2D/3D/кокпита

```text
       Shared client world state (from server snapshots)
              |              |             |
          2D view      External 3D     Cockpit view
              \              |             /
               same input/action command contract
```

На сервере **нет поля «текущий тип камеры»**. Переключение видов только на клиенте, не меняет состояние корабля. Разные способы ввода допустимы, но игровая возможность управлять, летать и взаимодействовать доступна в любом представлении. В 2D показать вертикальное смещение относительно выбранной плоскости и дать способ задавать вертикальное движение.

Сенсоры, обнаружение и выбор цели — отдельная логика от камер. Для M0 допустимо видеть все объекты тестовой системы, но UI должен быть спроектирован так, чтобы позже ограничить информацию по сенсорам.

## 6. Художественный прототип — часть качества M0

В M0 входит **настоящая управляемая демонстрация**, а не чёрный фон и кубик: освещённая звезда, красивая большая планета с кольцами или атмосферой, простая станция, астероидное поле, контраст масштаба, атмосферный свет и удобный HUD. Сцена должна использовать доступные процедурные/собственные материалы без сомнительных лицензий.

Тестировать производительность на Linux и доступном Vulkan-совместимом GPU среднего класса (ориентир RX 580 8 GB); предусмотреть минимум два пресета качества. Для первой версии не нужна продвинутая физическая достоверность и тяжёлые объёмные эффекты.

## 7. Задача масштабирования — после рабочего прототипа

300 игроков — **цель нагрузочного стенда**, не обещанная текущая ёмкость. Сразу отделять сетевой транспорт от симуляции, хранить идентификаторы систем/секторов, не отправлять всю галактику всем; позже — interest management, спящие системы, распределение по процессам.

На первом этапе не внедрять PostgreSQL, Kubernetes, репликацию БД, микросервисы, MMO-аккаунты и сложные persistence-слои без конкретной потребности. Для M0 можно держать мир в памяти.

## 8. Проверки

- `dotnet build` и `dotnet test` для независимых библиотек.
- Headless-запуск сервера на Linux.
- Godot-проект открывается в .NET-редакторе, проходит импорт и компилирует C#.
- Два клиента подключаются к одному серверу; отображают один мир и видят перемещение друг друга.
- Мгновенное переключение между 2D, внешней 3D и кокпитом сохраняет скорость/позицию корабля.
- Повторная проверка с отключённым интернетом возможна на localhost.
- Запуск подтверждён **реальными командами** в README; если редактор недоступен агенту, чётко отделять непроверенное от проверенного.
